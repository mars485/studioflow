# Структурированные заявки MODX → n8n → StudioFlow

Срез 26.10.2026. Собственный контракт StudioFlow, не копия API Аспро. Реализация и изолированные проверки не означают включения реальных форм.

## Наблюдение источника

Read-only MODX REST: `GET /rest/resources?limit=50&offset=0` вернул все 41 ресурса. GET ресурсов 7 (`audit`), 8 (`contacts`) и 28 (`lead-submit.html`) успешны. Обе формы указывают action `/lead-submit.html`; ресурс 28 вызывает `[[!ITG_LeadHandler]]`. Поля: `source`, `name`, `contact`, `website`, `message`, `privacy_consent`; у аудита дополнительно `email`, `audit_email_consent`. GET `/rest/snippets?name=ITG_LeadHandler&limit=1` вернул 405: код обработчика, его очередь и текущий получатель не исследованы. Формы не отправлялись, ресурсы не менялись. Нельзя отключать нынешнюю доставку.

## Контракт приёмки

- Новый серверный `POST /api/v1/integrations/website-leads`, тот же ограниченный токен `leads:create`, CSRF-заголовок и JSON/body limit 64 КиБ. Токены MODX/n8n для него непригодны. Проверки текущей роли/групп автора, квоты и выбранной воронки общие с прежним приёмником.
- Тело: UUID `request_key`, `form_kind` (`contact`/`audit`), `name`, `contact` (телефон либо контактная строка), необязательные email/website/message/company_name, HTTPS `source_url` на `itgsystem.ru` без query/fragment/credentials, `submitted_at` с timezone, строгие boolean-согласия, необязательная версия политики и пять UTM-полей.
- `privacy_consent` обязательно true. Аудит дополнительно требует email, website и `audit_email_consent: true`. Согласие на запрошенный аудит не является согласием на рекламу. Контекст — утверждение доверенного сервера-источника, не независимое доказательство клика пользователя; IP/UA не собираются.
- Для контактов нужен хотя бы `contact` или email. В телефон попадает только строка с допустимыми телефонными символами и 7–15 цифрами; Telegram/неоднозначная строка не выдаётся за телефон и сохраняется дословно в ограниченном контексте/описании.
- При наличии company_name создаётся COMPANY, иначе PERSON с именем заявителя, без выдуманных юридических реквизитов. Сайт переносится в профиль клиента/контакта; UTM — в существующие поля сделки. Внешние URL не загружаются сервером.
- `0029` добавляет nullable JSONB `website_context` в существующую квитанцию. Снимок источника, сайта, контакта, времени/согласий/UTM атомарен с CRM-операцией и сохраняется после изменения/удаления сделки или отзыва токена. Старые квитанции имеют null, согласия задним числом не создаются.
- Старый `/integrations/leads` и его digest не меняются. Общий UUID в workspace: повтор того же нормализованного тела возвращает прежние ID/200 без дубля, другие данные или другой контракт с тем же UUID — 409. Для новой заявки создаётся новый UUID; его и timestamp нужно сохранять до сетевых повторов на стороне источника.
- В admin-only журнале интеграций есть раскрываемый контекст без выполнения HTML/автоматической загрузки URL. MANAGER не получает журнал. Ошибка загрузки сохраняет обычный повтор; секреты не помещаются в контекст или экспорт workflow.
- Локальный draft n8n не активен, содержит placeholders для Credentials и `.invalid` назначения. Он не импортируется автоматически на рабочий n8n. Статические проверки экспорта не являются проверкой исполнения движком n8n.

## Границы

Нужны публичный адрес StudioFlow, тестовые workspace/воронка/токен, код и согласованный способ дополнения ITG_LeadHandler долговечной очередью. Имеющегося `/rest/resources` недостаточно для изменения PHP-обработчика. Публикация ресурсов, изменение обработчика, импорт/активация workflow, реальные отправки и перенос старых лидов требуют отдельного согласования. Управление контентом через MODX API остаётся отдельным сценарием с предпросмотром/версиями, а не произвольным PATCH из этого среза.

## Что готовит сервер сайта

Это **JSON-конверт сервер → сервер**, не исходный `application/x-www-form-urlencoded` POST браузера. Текущий обработчик пока не менялся.

1. Сохранить существующую валидацию формы/защиту от спама. Проверять согласия на сервере по действительным значениям checkbox, не подставлять true по умолчанию и не использовать `Boolean('false')`.
2. Нормализовать необязательные пустые поля в null/отсутствие. Сайт заявителя должен быть полным HTTP(S) URL без логина/пароля; без автоматического запроса этого URL.
3. Присвоить один UUID и время ISO 8601 с timezone **при принятии заявки**, сохранить их и тело в долговечной очереди до первой отправки. При повторе не генерировать новый UUID/время. Независимые заявки с разными UUID не объединяются по контактам.
4. Передать `form_kind` из известного серверу сценария, `source_url` без query/fragment. UTM — отдельно, из разрешённого набора. Не копировать произвольные browser headers/cookies, IP/UA или URL с секретами.
5. Ограничения: имя/контакт/версия политики — 100 символов, сайт/UTM/название компании — 255, страница-источник — 1024, сообщение — 8000, всё JSON-тело — 64 КиБ. Слишком длинный ввод не обрезается молча.

[Синтетический пример JSON](examples/website-audit.json). UUID/время в примере не переиспользовать для разных заявок; версия политики в нём демонстрационная, не действующее согласие посетителя.

## Локальный черновик n8n

Файл `frontend/public/integration-templates/itg-website-intake.draft.json` доступен для скачивания из раздела «Интеграции». Он **не импортировался** в `n8n.karpiev.ru` и не активировался.

Цепочка: header-auth Webhook → HTTP Request StudioFlow (повтор того же тела до трёх попыток, timeout 10 секунд, без redirect) → проверка UUID/совпадения request_key/boolean replayed и минимизация квитанции → acknowledgement. При ошибке или неверной квитанции положительного acknowledgement нет; источник сохраняет исходный конверт для последующего разбора/повтора. Это не долговечная очередь n8n: три попытки не заменяют очередь на стороне сайта.

Два **разных** Credentials должны быть выбраны оператором:

- Входящий webhook: отдельный случайный серверный ключ, например заголовок `X-ITG-Webhook-Key`. Не использовать здесь токен MODX, управляющий API-ключ n8n или токен StudioFlow.
- Исходящий HTTP Request: `Authorization: Bearer <ограниченный токен StudioFlow тестовой студии>`. Он не помещается в JSON-файл, тело или URL. `X-StudioFlow-Request: 1` уже указан в шаблоне.

Назначение `.invalid` требуется заменить на согласованный HTTPS endpoint **тестового** StudioFlow. Подключение Credentials, импорт и запуск — после подтверждения. Не указывать loopback API разработчика: удалённый n8n не имеет доступа к этому localhost.

Экспорт выключает сохранение данных успешных/ошибочных/ручных executions и progress. Это не отменяет настройки proxy, трассировки и журналов инфраструктуры — их нужно проверить отдельно. Acknowledgement содержит только принятие, UUID запроса/квитанции и флаг повтора, не копирует персональные данные и ссылки на CRM-объекты в публичный браузерный ответ.

Форма checkbox `audit_email_consent` разрешает только запрошенный аудит, не рекламную подписку. Автоматическая рассылка аудита, AI-обработка, скачивание сайта и подключение почтового провайдера в этот срез не входят.

## Совместимость и проверки

- Старый `/integrations/leads` принимает прежнее тело и сохраняет прежний SHA-256 digest. Добавление nullable-снимка не создаёт исторических согласий. Timestamp контекста нормализуется в UTC, email — в нижний регистр; подтверждённый повтор не расходует новую квоту.
- Контекст содержит персональные данные. Нет API редактирования/удаления отдельных квитанций и автоматической очистки; сроки хранения/экспорт для запроса субъекта данных требуют отдельного решения до production.
- Downgrade `0029` удаляет только колонку контекста, не клиента/контакт/сделку/квитанцию, но сохранённые согласия/UTM-снимок из этой колонки теряются. Перед откатом рабочей установки нужны резервная копия и согласованный экспорт; обратный upgrade не восстановит снимки.
- Backend: согласия и строгие boolean, URL/время/лимиты, PERSON/COMPANY, Telegram/телефон, UTM/профили, idempotency/конфликт/legacy-digest, роли/изоляция/группы/отзыв/квота, rollback, независимая конкурентность, upgrade/downgrade.
- Frontend: безопасный текстовый disclosure без загрузки URL/HTML, null у старых квитанций, reload, PERSON-подписи, статический контракт export и исполнение receipt guard на синтетических данных без сети.
- Итоговая общая регрессия после уточнения ISO-валидации и шаблона: **167/167 backend + миграции/`alembic check`, 104/104 frontend + production build, 34/34 E2E**. Браузер проверяет создание/повтор/409/журнал/reload/UTM/отзыв, скачивание draft и 390px. Ноль retries, четыре workers, прежний таймаут 30 секунд. Статические проверки шаблона и синтетический guard не заменяют импорт/исполнение в реальном движке n8n.

## Состояние на паузе

Пользователь подтвердил, что StudioFlow доступен только локально, а доступа к коду обработчика MODX пока нет. Внешняя активация блокируется этими условиями, независимые локальные модули можно продолжать отдельно. Затем пользователь попросил пока завершить работу: новый срез аудита каталогов не внесён. Оба disposable стенда остановлены командами `down`. `0029` не применялась к рабочей БД; ресурс сайта, обработчик, Credentials/активные workflow n8n не менялись. Изменения остаются локальными и не закоммичены/не опубликованы.
