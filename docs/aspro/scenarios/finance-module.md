# Сценарий: счета и акты со статусами оплаты

Приоритет: P2. Статус: TESTED (ограниченный объём ниже). Исследование: 23.10.2026; реализация: 24.10.2026.

Источник: `https://7e96.aspro.cloud/_module/fin/view/invoices` и `/_module/customdocs/view/index`. Evidence: `ev_fa114a529f6c7c358f26e4f0f48c5e44d930116357cddf912f64d18e7447f5e5` (список счетов и колонки), `ev_7c633799e67e308e99b897860d40ee3b5fd46e33d731f8477f9eb8cf300d602b` (печатные формы).

## Наблюдаемое поведение

«Список счетов»: кнопки «Автодействия», «Создать», настройки модуля, поиск. Колонки: №, Дата, Контрагент, Сумма счёта, Статус, Статус отправки, Организация, Менеджер, Акты, Проект, Сделка, Действие. Номер счёта — отдельная сущность со своим URL (`/fin/view/invoice/<id>`), контрагент связан с карточкой CRM.

«Документы» — библиотека печатных форм: формы для счетов, смет и актов, в том числе «Универсальная форма счёта РФ»; есть «Создать тип документа» и «Создать форму».

Установленные приложения расширяют модуль: Бюджетирование, Подотчёт, Кредиты и займы, Обязательства, Имущество, Автозагрузка и импорт банковских выписок.

## Что уже есть в StudioFlow

Реализован отдельный раздел «Финансы»: организации, счета, поступления, акты и собственная печатная форма. `Deal.amount` остаётся независимым.

## Объём первой итерации (P2)

1. Счёт как сущность workspace: номер (автонумерация в пределах workspace), дата, контрагент, сделка, проект, организация (реквизиты workspace), менеджер, сумма, валюта, статус.
2. Статусы счёта: черновик, выставлен, оплачен частично, оплачен, отменён. Отдельный признак «отправлен» с датой.
3. Платёж (поступление) со ссылкой на счёт; частичная оплата меняет статус.
4. Акт: связь со счётом, номер и дата, статус подписания.
5. Печатная форма счёта: собственный шаблон StudioFlow с реквизитами организации и контрагента, печать в PDF средствами браузера.
6. Список счетов с колонками №, Дата, Контрагент, Сумма, Статус, Проект, Сделка.

Не входит: сметы, бюджеты, подотчёт, кредиты, обязательства, имущество, банковские выписки, автодействия, ЭДО и юридически значимый документооборот.

## Модель данных и миграция

- `organizations` (`workspace_id` и реквизиты: название, ИНН, КПП, адрес, банк, расчётный счёт);
- `invoices` (`workspace_id`, `number`, `issued_on`, `client_id`, `deal_id`, `project_id`, `organization_id`, `manager_id`, `amount`, `currency`, `status`, `sent_at`);
- `invoice_payments` (`workspace_id`, `invoice_id`, `paid_on`, `amount`, `method`, `comment`);
- `acts` (`workspace_id`, `invoice_id`, `number`, `issued_on`, `status`, `signed_at`).

Автонумерация — последовательность в пределах workspace без гонок: уникальный индекс `workspace_id + number`.

### Реализация `0014_finance`

- `backend/app/models/finance.py`, `backend/app/api/v1/finance.py`, `finance_schemas.py`; UI `frontend/src/Finance.tsx`.
- Все финансовые маршруты (включая чтение) доступны только OWNER/ADMIN. MANAGER получает 403; чужой workspace/объект — 404. Это собственное консервативное правило StudioFlow, не установленное правило Аспро.
- `finance_counters`: атомарный PostgreSQL UPSERT для отдельной нумерации счетов и актов в workspace. Отменённые счета не удаляются, их номера не переиспользуются.
- Счёт создаётся неизменяемым черновиком; можно выставить или отменить. Частичная/полная оплата вычисляется из платежей, а не задаётся вручную. Оплаты только по выставленным счетам; отмена с платежами/актами запрещена. Для исправления неверного черновика отмените его и создайте новый.
- При платеже строка счёта блокируется: параллельные оплаты не могут превысить остаток. UUID `request_key` делает повтор платежа идемпотентным; тот же ключ с другими данными — 409.
- Реквизиты исполнителя и заказчика сохраняются снимками. Правка организации не меняет старые счета. ИНН/адрес заказчика вводятся в форме счёта; справочник клиентов пока не содержит налоговых реквизитов.
- Ссылка на сделку/проект проверяется в API и составным FK в БД. Отдельный FK `SET NULL` сохраняет счёт при удалении источника; составной FK отложен до конца транзакции, чтобы не зависеть от порядка триггеров PostgreSQL. Клиента/организацию со счетами удалить нельзя.
- Флаг отправки — только учётная отметка, не отправка email. Подписание акта — только учётная отметка, не ЭП. Печать/PDF через браузер: упрощённая форма без налогового расчёта, ЭДО и бухгалтерского учёта.
- Upgrade не меняет старые сделки/задачи/проекты. **Downgrade до `0013` удаляет финансовые таблицы и все их данные**: только после резервной копии, не как обычный способ отменить счёт.

## Критерии приёмки

1. Номер счёта уникален в workspace и не переиспользуется после отмены.
2. Частичная оплата переводит счёт в «оплачен частично», полная сумма — в «оплачен»; переплата отклоняется.
3. Счёт связан со сделкой и контрагентом; удаление связи не удаляет счёт.
4. Печатная форма содержит реквизиты организации и контрагента и не показывает данные чужого workspace.
5. Все маршруты workspace scoped; роль без прав на финансы получает 403.
6. Существующие сделки не меняются; `Deal.amount` остаётся независимым полем.

## Проверка

Проверки в одноразовых PostgreSQL и Docker-сетях:

- `backend/tests/test_finance.py`: статусы, копеечная точность, частичная/полная оплата, переплата, повтор платежа, снимки реквизитов, акты, все маршруты для MANAGER, чужие объекты, сохранение счёта после удаления источника.
- `backend/tests/test_finance_concurrency.py`: отдельная временная БД; 8 конкурентных счетов с разными номерами, конкурирующие оплаты и 4 повтора одного платежа в независимых транзакциях.
- `backend/tests/test_migrations.py`: upgrade с заполненными старыми сделками, задачами и напоминаниями, downgrade/повторный upgrade.
- `frontend/src/Finance.test.tsx`: список/печатные реквизиты/выставление, сохранность черновика при ошибке и повтор, создание организации, запрет загрузки финансов для менеджера.
- `frontend/e2e/finance.spec.ts`: счёт из сделки → частичная оплата → reload → полная оплата → подписанный акт → генерация PDF.
