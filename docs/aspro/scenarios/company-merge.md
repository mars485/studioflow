## Контракт и критерии приёмки

- Только OWNER/ADMIN выбранной студии. Полномочия повторно проверяются под блокировкой workspace, совместимой с отзывом membership.
- Исходная компания переносится в выбранную основную. Предпросмотр показывает обе карточки, направления переноса и количества связей. Слияние разных типов клиентов запрещено.
- Каждое поле (название, телефон, email, сайт, описание) по умолчанию остаётся от основной карточки; оператор явно выбирает поля исходной. Автоматического угадывания/удаления дублей нет.
- В одной транзакции переносятся сделки, проекты, счета, квитанции входящих заявок и связи контактов. Пересекающиеся связи контактов объединяются без дублей. ID сделок/проектов/счетов/контактов, задачи и файлы сохраняются.
- Снимки покупателя/продавца в выпущенных счетах, суммы, оплаты, акты, история и ключи идемпотентности заявок не переписываются.
- Исходная компания удаляется из рабочего каталога только после переноса. Полные исходные карточки и списки переносимых связей остаются в отдельном admin-only журнале; автоматического обратного слияния нет.
- При цепочке A → B → C журнал C включает исходные квитанции A → B без переписывания исторических ID; есть пагинация, цепочка не выходит за workspace.
- Подтверждение требует актуального fingerprint предпросмотра и UUID запроса. Изменившиеся поля/связи дают 409 и требуют нового предпросмотра. Повтор того же запроса возвращает прежнюю квитанцию, другой payload с тем же UUID — 409.
- Блокировки компаний/связей защищают перенос; deadlock/изменение ссылок приводят к откату и 409, а не частичному успеху.
- UI сохраняет выбор при ошибке, блокирует повторную отправку, отличает успешное слияние от неуспешного обновления списка и показывает квитанцию с автором/временем/исходными данными.
- Проверки: изоляция студий, MANAGER/неавторизованный, одинаковые/чужие/удалённые ID, устаревший предпросмотр, повтор/конфликт UUID, все связи и финансовые снимки, rollback, независимые конкурентные транзакции, миграция и браузерный сценарий.

Контакты как самостоятельные дубли в этом срезе не сливаются. Новая миграция применяется только в disposable тестовых БД; рабочая установка не обновляется автоматически.

## Использование и API

1. В каталоге «Клиенты» выбрать основную компанию → «Проверить дубли» → «Слияние» у кандидата. Останется компания, для которой запущена проверка; кандидат будет исходной. Для обратного направления закрыть форму и запустить проверку от другой компании.
2. Сверить названия/UUID, значения и количества связей. Отметить только поля, которые следует взять из исходной; выбор пустого значения также означает явную замену на пустое.
3. Поставить подтверждение и выполнить слияние. При сетевой ошибке повторить тот же запрос; при 409 обновить предпросмотр и подтвердить заново.
4. В карточке основной компании открыть «История слияний». Квитанции содержат автора/время/исходные значения, доступны только OWNER/ADMIN, включая после reload и цепочки слияний. Автоматической отмены нет.

- `POST /api/v1/workspaces/{workspace_id}/client-merges/preview`: `source_id`, `target_id`; ответ содержит карточки, количества связей и `preview_version`.
- `POST /api/v1/workspaces/{workspace_id}/client-merges`: те же ID, `preview_version`, UUID `request_key`, `confirmed: true`, `source_fields` из `name/phone/email/website/notes`; возвращает квитанцию. Не принимает произвольные поля/чужой workspace через тело.
- `GET /api/v1/workspaces/{workspace_id}/client-merges?target_id=...&limit=20&offset=0`: журнал с учётом исторической цепочки; максимум 100 квитанций на страницу.

Миграция добавляет только пустую таблицу журнала; существующие данные при upgrade не меняет. Downgrade удаляет журнал, **не отменяет выполненные слияния**: перед ним нужен экспорт квитанций и резервная копия. Применение к рабочей БД требует отдельной операции, не выполняется этим изменением.
