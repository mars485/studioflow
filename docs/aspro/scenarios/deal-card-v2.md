# Сценарий: карточка сделки v2

Приоритет: P1. Статус: TESTED (backend 42/42, frontend 28/28, E2E 1/1, сборка). Дата исследования: 23.10.2026, реализация 23.10.2026.

Источник: авторизованный демо-портал `https://7e96.aspro.cloud/`, карточка `/_module/crm/view/lead/10?tab=lead_info`. Evidence: `ev_97ac6b8b659b21aceb5b23c1717b735912cd77906caa694178a2be2ab9d17493` (состав вкладок, поля, UTM, пользовательские поля, лента).

## Наблюдаемое поведение

Карточка сделки имеет вкладки: Общие, Документы, Финансы, Дела, Почта, Звонки, Автодействия, Списки. Шапка: название сделки, кнопки «Создать», «Документ», отправка письма.

На вкладке «Общие»:

- полоса стадий воронки с действием «Завершить сделку»;
- поля: Сумма, Сроки сделки (начало–окончание), Источник сделки, Ответственный;
- блок «Клиент»: компания с телефоном и e-mail, список контактов с отметкой «контакт не из компании», кнопка «Выбрать контакт»;
- «О сделке»: описание, связь со списком, связь с проектом, вложения;
- теги, наблюдатели (в наблюдаемом примере «Нет наблюдателей» и «Добавить наблюдателя»);
- блок «Дополнительно»: компания, контактное лицо, должность, телефон, мобильный телефон, e-mail, сайт;
- UTM-метки: `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `http_referrer`;
- пользовательские поля (в примере «Автонумерация», «Тип услуги»);
- лента с композером: Комментарий, Призвать к ответу, E-mail, Задача, Событие; запись ленты содержит автора, время и признак «Запланировано».

## Что уже есть в StudioFlow

Модель `Deal`: `title`, `client_id` (обязателен), `contact_id`, `pipeline_id`, `stage_id`, `responsible_user_id`, `amount`, `currency`, `description`, `contact_name`, `source`, `start_date`, `end_date`, `follow_up_*`. Есть `DealActivity` (заметки и смена стадии), `DealTask` с напоминаниями (`TaskReminder`), `FollowUpCompletion`, `ContactClient`.

Чего нет: тегов, наблюдателей, вложений, связанного проекта, UTM, пользовательских полей, композера задач и событий из карточки, вкладок «Документы», «Финансы», «Почта», «Звонки», «Автодействия», «Списки».

## Объём первой итерации (P1)

Входит:

1. Композер активностей: комментарий, задача (создаёт `DealTask`), событие (запись без срока в `DealActivity`), «Призвать к ответу» (упоминание участника workspace).
2. Теги сделки: справочник тегов workspace и связь many-to-many со сделкой.
3. Наблюдатели: связь сделки с участниками workspace.
4. Несколько контактов у сделки: замена одиночного `contact_id` набором связей с сохранением текущего поля для совместимости.
5. Вложения: метаданные файла (имя, размер, тип, автор, время) без внешнего хранилища на первом шаге.
6. UTM-поля и произвольные пользовательские поля сделки (ключ-значение с типами: текст, число, дата, справочник).

Не входит (отдельные сценарии): документы и печатные формы, финансы, почта и звонки, автодействия, списки, воронка из карточки.

## Модель данных и миграция

Новая миграция `0011` (следующая после `0010_task_reminders`):

- `deal_tags` (`id`, `workspace_id`, `name`, уникальность `workspace_id + name`, нормализованное имя);
- `deal_tag_links` (`workspace_id`, `deal_id`, `tag_id`, каскадное удаление связи, ограничение уникальности);
- `deal_watchers` (`workspace_id`, `deal_id`, `user_id`, проверка membership);
- `deal_contacts` (`workspace_id`, `deal_id`, `contact_id`, `is_primary`);
- `deal_attachments` (`workspace_id`, `deal_id`, `filename`, `content_type`, `size_bytes`, `uploaded_by`, `created_at`);
- `deal_custom_values` (`workspace_id`, `deal_id`, `field_key`, `field_type`, `value_text`, `value_number`, `value_date`);
- поля `deals.utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `http_referrer`.

Все таблицы получают составной внешний ключ по `workspace_id`, как в существующих сущностях.

## API

Расширение `backend/app/api/v1/crm.py`, все маршруты workspace scoped:

- `GET /tags`, `GET/POST /deals/{deal_id}/tags`, `DELETE /deals/{deal_id}/tags/{tag_id}` — имя тега уникально в workspace без учёта регистра; удаление связи не удаляет тег;
- `GET/POST /deals/{deal_id}/watchers`, `DELETE /deals/{deal_id}/watchers/{user_id}` — только активный участник workspace, повторное добавление отклоняется;
- `GET/POST /deals/{deal_id}/contacts`, `PATCH /deals/{deal_id}/contacts/{contact_id}` (основной контакт), `DELETE` (основной переносится на старейшую связь);
- `GET/POST /deals/{deal_id}/attachments`, `DELETE /deals/{deal_id}/attachments/{attachment_id}` — только метаданные: имя, тип, размер, автор;
- `GET/PUT /deals/{deal_id}/custom-fields` с телом `{"values":[{"key","type","value"}]}`, типы `TEXT | NUMBER | DATE`, ключи уникальны без учёта регистра, неверное число или дата отклоняются;
- `PATCH /deals/{deal_id}` принимает `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `http_referrer`;
- `POST /deals/{deal_id}/activities` принимает `kind`: `NOTE | EVENT | MENTION` (смена стадии остаётся системной `STAGE_CHANGE`).

## UI

Новый компонент `frontend/src/DealDetails.tsx` в карточке сделки: теги, наблюдатели, связанные контакты с выбором основного, вложения, UTM-метки и пользовательские поля. Композер истории получил выбор типа записи (комментарий, событие, призыв к ответу), задачи по-прежнему создаются в блоке задач. Ошибки: 403 на роль без прав, 404 на чужую сделку, 409 на дубль тега или наблюдателя, 422 на неверный тип поля; у каждой секции есть повтор загрузки.

## Критерии приёмки

1. Комментарий, задача и событие из карточки сохраняются с автором и временем и видны после перезагрузки.
2. Задача, созданная из карточки, появляется в «Мой день» по тем же правилам, что и `DealTask`.
3. Тег нельзя создать дублем в пределах workspace; удаление тега не удаляет сделку.
4. Наблюдателем может стать только активный участник workspace.
5. Несколько контактов: основной ровно один; удаление контакта из сделки не удаляет контакт.
6. UTM и пользовательские поля сохраняются и отдаются в API; неверное значение для типа `NUMBER` или `DATE` отклоняется, повтор ключа без учёта регистра отклоняется.
7. Чужой workspace и чужая сделка недоступны ни на одном новом маршруте.
8. Существующие сделки и связи не меняются; миграция проходит на чистой БД и обратно совместима по `contact_id`.
