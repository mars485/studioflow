## Наблюдаемое поведение

- Один и тот же набор задач показывается в пяти представлениях: Планирование, Канбан, Список, Гант, Календарь.
- Сверху выбирается рабочий процесс; по умолчанию колонки «Сделать», «В работе», «Ожидает контроля», «Завершено» с числом задач и суммой планового времени.
- Карточка задачи на доске показывает проект или сделку, теги, относительный срок, прогресс чек-листа, плановое и потраченное время, исполнителя, признак важности.
- Форма: название (обязательно), приоритет, описание, чек-лист, файлы, ответственный, постановщик, соисполнители, наблюдатели, даты начала и крайнего срока, рабочий процесс, контроль после выполнения, подзадачи, оценка времени, теги, связь с проектом/сделкой/контрагентом, напоминание, регулярное повторение.
- «Выбрать несколько» рядом с ответственным создаёт отдельную задачу для каждого выбранного.

## Что уже есть в StudioFlow

`DealTask` — задачи только внутри сделки: название, описание, приоритет, статус, исполнитель из участников, даты, автор завершения. `TaskReminder` — напоминания. Отдельного модуля задач, представлений и операций вне сделки нет; экран «Задачи» демонстрационный.

## Объём первой итерации (P2)

1. Задача как самостоятельная сущность workspace со связями (сделка, контрагент, проект) и без них.
2. Представления: Список и Канбан (Планирование, Гант, Календарь — отдельными итерациями).
3. Рабочие процессы: настраиваемые статусы workspace с порядком и защитой используемого статуса.
4. Чек-лист задачи (пункты с отметкой) и оценка времени.
5. Подзадачи одного уровня вложенности.
6. Наблюдатели задачи.
7. Перенос существующих задач сделки в новую модель с сохранением поведения карточки сделки и напоминаний.

Не входит: регулярные задачи, несколько исполнителей с копированием задач, трудозатраты по таймеру, Гант и Календарь, контроль после выполнения, связь с проектом (модуль проектов ещё не реализован), теги задач и соисполнители.

## Модель данных и миграция

Реализовано миграцией `0012_task_module`:

- `task_statuses` (`workspace_id`, `name`, `position`, `is_final`) с четырьмя статусами по умолчанию: «Сделать», «В работе», «Ожидает контроля», «Завершено»;
- `tasks` (`workspace_id`, `title`, `description`, `status_id`, `priority`, `assignee_user_id`, `creator_user_id`, `start_at`, `due_at`, `estimate_minutes`, `deal_id`, `contact_id`, `parent_task_id`, `completed_at`, `completed_by_user_id`);
- `task_checklist_items` (`workspace_id`, `task_id`, `text`, `is_done`, `position`);
- `task_watchers` (`workspace_id`, `task_id`, `user_id`).

Перенос данных: `deal_tasks` → `tasks` с сохранением идентификаторов, авторов, сроков и завершения; внешний ключ `task_reminders` переведён на `tasks`, затем `deal_tasks` удалена. Откат восстанавливает `deal_tasks` из `tasks` (задачи без сделки при откате не восстанавливаются).

## Критерии приёмки

1. Задача создаётся вне сделки и с привязкой к сделке; в карточке сделки видна та же задача.
2. Канбан и Список показывают одни и те же данные; смена статуса сохраняется.
3. Исполнитель и наблюдатели — только активные участники workspace.
4. Крайний срок не раньше даты начала; завершение фиксирует автора и время.
5. Статус, который используется задачей, нельзя удалить.
6. Чек-лист: прогресс пересчитывается и отображается в списке.
7. Чужой workspace, чужая задача и чужой статус недоступны.
8. Существующие задачи сделок и напоминания после миграции работают как прежде.

## API и UI

Backend (`backend/app/api/v1/crm.py`), все маршруты workspace scoped:

- `GET/POST /task-statuses`, `PATCH/DELETE /task-statuses/{id}`, `PUT /task-statuses/order` — только владелец и администратор; статус с задачами удалить нельзя; должен остаться завершающий статус;
- `GET/POST /tasks`, `GET/PATCH/DELETE /tasks/{id}` — фильтры `deal_id`, `contact_id`, `status_id`, `assignee_user_id`, `parent_task_id`, `include_done`; удаление только для владельца и администратора;
- `GET/POST /tasks/{id}/checklist`, `PATCH/DELETE /tasks/{id}/checklist/{item_id}`;
- `GET/POST /tasks/{id}/watchers`, `DELETE /tasks/{id}/watchers/{user_id}`;
- завершение задачи фиксирует автора и время при переходе в завершающий статус и очищает их при возврате;
- старые маршруты `/deals/{id}/tasks` сохранены как совместимый вид: `status` отдаётся как `OPEN | DONE`, а `PATCH {"status": "DONE"}` переводит задачу в завершающий статус.

Frontend: новый экран `frontend/src/Tasks.tsx` (пункт меню «Задачи») с представлениями Канбан и Список, созданием задачи, карточкой задачи (поля, чек-лист, подзадачи, наблюдатели) и настройкой статусов для администраторов.

## Проверка

Выполнено 23.10.2026 в изолированном контейнере `docker-compose.test.yml`:

- миграция `0012` применилась на чистой PostgreSQL, `alembic check` не нашёл расхождений;
- backend: 45 тестов, все прошли; новые тесты покрывают статусы, порядок, защиту от удаления, задачи, подзадачи, чек-лист, наблюдателей, совместимость задач сделки и напоминаний;
- frontend: 31 тест, сборка `npm run build` прошла;
- E2E `docker-compose.e2e.yml`: цепочка «регистрация → сделка → follow-up → перезагрузка» прошла, 1/1.

Права ролей Аспро на каждое действие, лимиты, правила повторения, представления Гант и Календарь, уведомления, соисполнители и теги задач.
