# Регрессия связей задач и проектов

Срез 24.10.2026. Это исправления ранее реализованных сценариев, а не новые функции Аспро.

## Исправлено

- Статусы задач создаются только при пустом процессе под блокировкой workspace. Переименованный/удалённый исходный статус больше не появляется снова при GET.
- Изменения процесса сериализованы по workspace, чтобы два запроса не удалили последние завершающие статусы одновременно. Признак завершения статуса с задачами менять нельзя: сначала перенесите задачи. История завершения существующих задач не переписывается.
- PATCH с `is_final: null` или `is_done: null` возвращает 422, а не нарушение NOT NULL в БД.
- Пагинация списка задач выполняется в SQL, не после загрузки всех записей.
- Создание проекта блокирует исходную сделку до проверки дубля. Переносятся и связанные контакты, и прежний основной `Deal.contact_id`, без дублей.
- ORM-ограничение типов активности приведено в соответствие с уже применяемой миграцией `0011`: NOTE/STAGE_CHANGE/EVENT/MENTION. MENTION по-прежнему только тип записи, не уведомление получателя.
- Миграция `0015_workspace_link_guards`: восстановлены составные workspace-FK для задача→проект/контакт/родитель и проект→сделка. Отдельные `SET NULL` сохраняют запись при удалении источника, отложенные составные FK запрещают межпространственные ссылки. Удаление родителя сохраняет подзадачу, снимая родительскую связь; родитель не может совпадать с самой задачей.

## Сохранность данных

Миграция не исправляет и не удаляет данные автоматически. Если исторические ссылки уже неверны/осиротели, добавление ограничений остановится транзакционно. Сначала исследуйте такие записи и отдельно согласуйте исправление. Downgrade `0015` снимает только новые ограничения, сохраняя записи.

## Проверки

- `test_tasks.py`: сохранность переименования/удаления статуса, nullable PATCH, защита используемого статуса, сохранение подзадачи при удалении родителя, прямой запрет чужих ссылок в БД.
- `test_projects.py`: перенос прежнего основного контакта без дополнительной связи.
- `test_migrations.py`: заполненные сделки, старые задачи и напоминания проходят upgrade до head и обратный переход до `0010`, затем повторный upgrade.
- `frontend/e2e/projects.spec.ts`: выигранная сделка → проект → перенос контакта → задача в проекте и общем разделе → reload → архив.

## Оставшиеся ограничения

Календарь/повторения/учёт времени, Гант/порядок работ/шаблоны, реальные файлы, синхронизация старого основного контакта со всеми новыми связями, полноценные уведомления, автоматизации и интеграции не входят в этот срез. Миграция `0012` при downgrade теряет самостоятельные задачи: откат рабочей базы без резервной копии недопустим.
