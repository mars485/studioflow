# Адресные упоминания и входящие уведомления

P1/P2, TESTED в описанном объёме. В карточке референса наблюдался композер «Призвать к ответу»; прежде StudioFlow сохранял только ярлык MENTION. Доставка и интерфейс ниже — самостоятельная реализация, без предположений о правилах Аспро.

- Новая запись MENTION требует одного активного участника выбранного workspace. Автор и имя адресата сохраняются в истории; старые безадресные записи не меняются.
- Уведомление создаётся в той же транзакции, что и активность. Нет email/push и внешних отправок.
- Раздел «Уведомления»: рабочее пространство, непрочитанные/все, пагинация, обновление, отметка о прочтении и «Прочитать все», переход в нужную сделку.
- API возвращает только уведомления текущего пользователя в доступном workspace. При удалении membership его уведомления удаляются, доступ отзывается; история сделки остаётся.
- При удалении активности/сделки связанные уведомления удаляются каскадно. Самоупоминание допускается. Изменение имени пользователя не переписывает историю.

Приёмка: упомянутый участник видит уведомление после reload, другой участник не видит; отметки read сохраняются; удалённый участник не получает доступ; NOTE/EVENT не создают уведомления; чужой/неактивный получатель отвергается. Миграция сохраняет старые активности.

Реализация: `0017_mention_notifications`, `notifications.py`, `Notifications.tsx`, выбор адресата в CRM. Входящие хранятся с составными FK к membership и активности. Обновление явной кнопкой, страницы по 50 записей. Старые MENTION без адресата остаются только историей и не доставляются задним числом.

Проверено 24.10.2026: `test_notifications.py` (3 сценария), `Notifications.test.tsx` (3), `e2e/notifications.spec.ts` — два изолированных браузерных аккаунта, личный inbox, переход в студию с несколькими workspace и read после reload. Срез: backend 64/64, frontend 48/48 + build, E2E 6/6. Локальная dev-база обновлена до `0017` после `pg_dump`. Downgrade удаляет inbox и адресные поля, но сохраняет текст активностей.
