# Исходящие события и повторная доставка webhook

P2, TESTED в описанном объёме. [Справка Аспро: отправка данных](https://aspro.cloud/help/articles/3301-3300-3322--avtodejstvie-vebhuk) и [webhook задач](https://aspro.cloud/help/articles/3281-6625-6657--webhook) подтверждают сценарий отправки событий. Контракт, очередь и политика доставки ниже — собственные StudioFlow, не совместимость с API Аспро.

- OWNER/ADMIN подписывается на `deal.created`, `deal.stage_changed`, `task.completed`. Событие и очередь доставки сохраняются в транзакции изменения объекта; нет сетевого вызова внутри CRM-запроса.
- Payload v1 содержит ID события, тип, время, workspace и ID объекта; для перехода — ID старой/новой стадии. Имена, телефоны, комментарии, файлы, суммы и токены не отправляются. Получателю нужна отдельная авторизация, если он хочет читать CRM.
- Адреса задаются оператором через `WEBHOOK_DESTINATIONS` (JSON словарь метка → HTTPS URL), не пользователями через произвольный URL. Без конфигурации и ключа `WEBHOOK_SIGNING_KEY` исходящие webhook выключены. Реальные адреса не предполагаются и не добавляются автоматически.
- Только HTTPS:443, без credentials/query/fragment; DNS проверяется перед каждой попыткой, все IP должны быть публичными. Соединение закреплено за проверенным IP, Host/TLS SNI остаётся исходным. Нет redirect, proxy из окружения, cookies и ответа в журнале. Дополнительно рекомендуется egress firewall.
- HMAC-SHA256: `X-StudioFlow-Timestamp` и `X-StudioFlow-Signature: sha256=<hex>` от `timestamp + '.' + raw_body`. Ключ подписки показывается один раз при создании и получается HMAC-деривацией из серверного ключа и ID подписки. Смена серверного ключа меняет подписи всех подписок; получателей нужно перенастроить.
- Отдельный worker `python -m app.webhook_worker` обрабатывает до 20 доставок за запуск. Планировщик/сервис должен запускаться оператором; API и dev не запускают исходящие отправки сами.
- Успех только 2xx; до 5 попыток с задержкой 1/2/4/8 минут. Общий сетевой timeout 10 секунд, тело ответа не читается/не сохраняется. Журнал содержит безопасный код результата, статус и количество попыток, ручной повтор FAILED возвращает запись в очередь.
- Доставка как минимум один раз: после сетевого успеха и до commit возможен повтор. Получатель проверяет HMAC, возраст timestamp и дедуплицирует `event_id`. Отключение подписки или потеря автором роли OWNER/ADMIN отменяет ожидающую доставку. Membership удаляет подписку/очередь; CRM-объекты не удаляются.
- Потерянный ключ: отключить подписку, явно удалить её вместе с журналом доставки и создать заново. Это выдаёт новый ключ; CRM-объекты не меняются. Включение обратно не восстанавливает отменённые доставки.
- Адреса не должны содержать секретов даже в path. Смена назначения в конфигурации меняет получателя будущих попыток, включая очередь: сначала отключите старую подписку и согласуйте нового получателя. Срок хранения журнала и частоту запуска worker оператор выбирает отдельно; автоматической очистки нет.

Приёмка: транзакционное событие, isolated workspace/roles, фиктивный transport 2xx/ошибка/timeout/redirect, отложенные/ручные повторы, два worker не отправляют одну запись одновременно; private DNS/IP не вызывают HTTP. Внешние endpoint и n8n не подключаются без реальной конфигурации пользователя.

Проверено 24.10.2026 в общем срезе backend 92/92, frontend 66/66 + build, E2E 8/8 (включая соседнюю аналитику). `test_webhooks.py` — события/права/отмена, повторы, подпись и закреплённые IP/Host/SNI, запрет private DNS/redirect. `test_webhook_concurrency.py` — rollback очереди и конкурирующие worker на независимых транзакциях одноразовой БД. `Webhooks.test.tsx` — конфигурация и одноразовый ключ. В `e2e/integrations.spec.ts` подписка на test-only `.invalid` → входящая заявка → ровно одна PENDING-доставка → отключение/CANCELLED. Worker в браузерном стенде не запущен, сеть `internal: true`, внешних отправок нет. Реальный TLS endpoint не проверен: transport подставной, поддержка SNI сверена с установленным httpcore.

`0024` применена к dev после `studioflow-before-0024-20261024.dump`. Downgrade удаляет подписки/очередь, не CRM-объекты. Число попыток относится к текущему циклу доставки; ручной повтор FAILED сбрасывает его. Это не полный неизменяемый аудит попыток и не общий конструктор автоматизаций.
