# Группы сотрудников и ограничение изменений

26.10.2026. Первый безопасный срез гибких прав, не полный RBAC референса.

REA `ev_8b076471aa1dea782b065d2b7d753e33118652a275039b606526f2ffeb0afaf3` подтверждает раздел «Команда», вкладку «Группы пользователей» и отдельную настройку прав сотрудника. Настройки не сохранялись. Раздел «Группы» рабочего пространства не приравнивается автоматически к группам пользователей. Серверные правила наследования/разрешений Аспро не исследованы; ниже собственный контракт StudioFlow.

## Контракт

- Группа принадлежит одной студии, содержит название/описание, участников из текущего membership, версию и перечень запрещённых изменений по модулям: CRM, клиенты, задачи, проекты, финансы, интеграции.
- Без групп существующие роли работают как раньше. Группы могут только **ограничить**, но не расширить полномочия роли. Запрет из любой группы побеждает разрешение другой. Это не изоляция чтения: все ранее доступные чтения остаются доступными.
- OWNER не блокируется групповыми запретами: владелец может восстановить настройки. Только OWNER создаёт/изменяет группы и состав/ограничения. ADMIN читает состав/настройки, MANAGER видит только собственные эффективные ограничения через отдельный API. Защита последнего владельца не меняется.
- Изменения групп сериализованы с изменяющими API-запросами через блокировку workspace и повторную проверку membership. Версия защищает от сохранения устаревшей формы. Отзыв membership удаляет связи групп каскадом, не удаляет бизнес-данные.
- ADMIN не может удалить участника с действующими групповыми запретами: иначе удаление и повторное добавление сняло бы политику OWNER через каскад membership. Удалить такого участника может OWNER. Для участников без запретов прежнее управление MANAGER администратором сохраняется.
- Ограничения проверяются сервером в общей зависимости доступа на всех изменяющих workspace-маршрутах. Вложенные API задач сделки учитывают CRM и задачи; слияния требуют все затрагиваемые модули. Просмотр слияния, отметки чтения личных уведомлений и административные настройки доступа не являются изменением бизнес-модуля.
- Неизвестный изменяющий бизнес-маршрут при активных ограничениях запрещён по умолчанию. Новые маршруты должны включаться в явную классификацию и её тесты.
- Входящие интеграционные заявки отдельно учитывают ограничения действующего автора токена для CRM/клиентов/интеграций, включая повторы. Настройки внешних отправок не включаются. Worker доставки остаётся отдельной операторской операцией, не пользовательским API группы.
- Журнал изменений групп транзакционный: тип операции, ID группы, автор/время и имена полей без значений/списков участников/секретов. Переживает удаление группы и отзыв автора; это пока не общий аудит всех модулей.
- UI в настройках: явное открытие, список, создание/редактирование/удаление OWNER, ADMIN только просмотр, объяснение границ и «запрет побеждает», ошибки/повтор/сохранение черновика. Существующие формы модулей показывают серверный 403 и сохраняют ввод; массовая переработка всех кнопок под новые ограничения не заявляется.

## Проверки

Миграция без backfill/изменения ролей; ограничения БД на workspace; CRUD и версии; чужие участники; роли/отзыв; отсутствие расширения MANAGER; объединение запретов; все маршруты классифицированы; вложенные маршруты/слияния/входящие токены; блокировки и журнал/rollback; UI и браузерный сценарий с двумя пользователями.

Нет произвольных пользовательских ролей, разрешений отдельных записей/полей, групповой изоляции чтения и общесистемного аудита. Эти пункты остаются следующими срезами.

## Использование и API

«Настройки» → «Открыть группы сотрудников». OWNER выбирает состав и модули с запретом изменений; ADMIN видит список без действий изменения. При конфликте версии форма не перезаписывается автоматически: обновить список и открыть запись заново. Нельзя применять ограничения чтения через эти флажки.

- `GET /workspaces/{workspace_id}/group-permissions`: собственная роль, эффективные запреты, поддерживаемые действия, флаг освобождения OWNER; не выдаёт дополнительных разрешений роли.
- `GET /groups`, `POST /groups`, `PUT /groups/{id}` (с `expected_version`), `DELETE /groups/{id}?expected_version=...` под тем же workspace-префиксом. Максимум 200 групп, 500 участников в группе, шесть поддерживаемых запретов; имена уникальны внутри студии.
- `GET /groups/audit?limit=50&offset=0`: admin-only журнал без значений полей/секретов.

Проверка запретов находится в общей зависимости `workspace_member`, поэтому охватывает и прямые зависимости учёта времени/таймера. Отдельный тест перечисляет все изменяющие workspace-маршруты и требует явной классификации. Ранее обнаруженный пробел зависимости таймера исправлен; целевые backend-проверки групп/конкурентности прошли 7/7. Двухпользовательский E2E проверяет запрет → 403 с сохранением черновика → снятие запрета → успех, мобильную ширину и журнал.
