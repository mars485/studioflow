## Критерии приёмки

- Только OWNER/ADMIN, повторная проверка membership под блокировкой workspace. Разные существующие контакты одной студии; компании и контакты не смешиваются.
- Предпросмотр обеих карточек и количества связей. По умолчанию значения основной карточки сохраняются; явно можно перенести имя, фамилию, отчество, телефон, email, сайт, описание (в том числе пустое необязательное поле).
- В одной транзакции объединяются связи с компаниями, дополнительные контакты сделок и контакты проектов; прямые ссылки задач и основные контакты сделок переназначаются. Общие связи не дублируются.
- Если исходный контакт был основным в сделке, основным становится целевой. Если основным был третий контакт, он не меняется. `Deal.contact_id`, `contact_name` и `DealContact.is_primary` остаются согласованными, в том числе при изменении имени основной карточки.
- Несогласованная прежняя конфигурация основного контакта отклоняется с 409 вместо потери связей. Предпросмотр фиксирует состояние ссылок и основных контактов; изменения после просмотра требуют нового подтверждения.
- ID сделок/задач/проектов, суммы, сроки, файлы, оплаты/счета/история не пересоздаются. Существующий аудит сделок фиксирует изменения `contact_id`/`contact_name`.
- Исходный контакт удаляется из рабочего каталога только после переноса. Журнал `0027` сохраняет обе полные карточки, исходные связи/основные контакты, автора, время и выбор полей. История цепочки A → B → C доступна из C с пагинацией, только администраторам.
- UUID запроса обеспечивает идемпотентность; конфликт UUID/устаревший просмотр — 409. Блокировки/rollback защищают от параллельного частичного переноса.
- UI требует явное подтверждение, не теряет выбор при сетевой ошибке, повторяет тот же UUID, не повторяет операцию после успешного слияния при ошибке обновления списка. MANAGER не видит действий слияния и журнала.
- Тесты: все типы ссылок и пересечения, третий основной контакт, смена имени, изоляция/роли, устаревший просмотр, UUID, rollback, независимая конкурентность, миграция и браузер/reload/мобильная ширина.

Автоматического слияния и отмены нет. Downgrade удаляет квитанции, не восстанавливает разделённые контакты; перед откатом нужны резервная копия и экспорт. Рабочая БД не обновляется в рамках тестов.

## Проверки и использование

В разделе «Клиенты» → «Контакты» запустить проверку дублей от основной карточки, открыть «Слияние» у кандидата. Основной останется карточка, от которой запущена проверка. Проверить поля/связи, отметить нужные поля и отдельное подтверждение. История доступна в карточке контакта и после reload.

API повторяет контракт компаний: `POST /workspaces/{workspace_id}/contact-merges/preview`, `POST /contact-merges` с `source_id`, `target_id`, `preview_version`, UUID `request_key`, `confirmed: true` и `source_fields`; `GET /contact-merges?target_id=...&limit=20&offset=0` для истории, максимум 100 квитанций на страницу.

Промежуточный полный backend: 129/129 + миграции/`alembic check`; frontend 93/93 + build. После исправления тестовой подготовки проекта (контакты проекта переносятся из выигранной сделки, а не добавляются несуществующим POST) целевые браузерные сценарии контактов и P0 CRM прошли 2/2. Итоговая общая регрессия после групп: **136/136 backend + миграции/`alembic check`, 97/97 frontend + build, 33/33 E2E**. TESTED в описанном объёме; не VERIFIED-соответствие серверным правилам Аспро.
