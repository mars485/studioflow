## Что требуется для внешних подключений

Не хранить секреты в этом файле, репозитории или чате. Передать их оператору через приватное окружение/хранилище секретов после выбора провайдеров.

- Сайт ITG: `https://itgsystem.ru`, MCP `https://mcp.itgsystem.ru/mcp`. Remote OAuth-подключение `itg-site` добавлено в конфигурацию проекта; endpoint требует авторизации (`401`, OAuth discovery доступен). Вход через `/mcps` заблокирован отсутствием динамической регистрации клиента; нужны Client ID и разрешённый loopback Redirect URI заранее зарегистрированного клиента (секрет confidential-клиента — только приватно). Затем нужны доступный код формы/сервера, тестовое окружение, нужная студия/воронка, карта полей и согласие на обработку данных.
- Альтернативный MODX REST endpoint `https://itgsystem.ru/rest/resources` проверен: Bearer из приватной `MODX_API_TOKEN` → 200, без токена → 401; 20 ресурсов в выдаче, `total: 41`. Чтение контента доступно без MCP, но права/контракты записи и API заявок пока не исследованы. Формы, публикация и CRM-подключение не изменялись.
- n8n: `https://n8n.karpiev.ru`; новый ключ найден в пользовательской переменной `N8N_API_KEY`. Read-only API проверен: health и список workflow — 200; доступны 20 workflow (3 активны). MAIN/CONTACT просмотрены структурно, без параметров/секретов и запуска. Нужны согласованный тестовый workflow/HTTPS webhook, события и данные; действующие workflow для других сервисов не заменять. Секрет HMAC настраивается приватно с обеих сторон. По умолчанию worker не включается.
- Почта: провайдер, домен/отправитель, тестовый ящик, SPF/DKIM/DMARC; правила входящей почты, хранения и разрешённые получатели.
- Телефония: провайдер/тестовый аккаунт, номера, события звонка, политика записей и прав доступа.
- Push: домен приложения, выбранный канал/provider, подписка/отписка и согласие получателя.
- Банки/бухгалтерия: банк, формат выписки/API, продукт и версия бухгалтерии (например 1С), тестовая организация, read-only доступ и правила сверки/защиты от повторов.
- Перед реальной отправкой: проверка тестового получателя, HTTPS/HMAC, дедупликации и ошибок; отдельное подтверждение production/deploy. Отсутствие этих данных не блокирует независимые локальные модули.

Реальные подключения и production этим планом не включаются. REA/CDP восстановлен в отдельном профиле после ручного входа пользователя; неизвестные правила референса по-прежнему не выдаются за исследованные.
