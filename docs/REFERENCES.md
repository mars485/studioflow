# StudioFlow — референсы Flowlu и Аспро.Cloud

> Статус: проектный ориентир, не спецификация копирования. Обновлено: 2026-10-22.  
> Репозиторий: `mars485/studioflow`. Стек: FastAPI / SQLAlchemy / PostgreSQL / Alembic / React / TypeScript / Docker.

## 1. Цель и принципы

Развивать StudioFlow как самостоятельную CRM/ERP для ITG и веб-студий, опираясь на функциональные сценарии Flowlu и Аспро.Cloud. Не копировать код, фирменные элементы, изображения, тексты и точную компоновку экранов. Проверять доступность и поведение функций в актуальных версиях референсов перед реализацией.

- **Flowlu** — референс связности CRM → задачи → проекты → счета, автоматизаций и организации бизнес-процессов.
- **Аспро.Cloud** — референс ежедневной работы менеджера: воронки, карточки, контакты, задачи и удобная навигация.
- **StudioFlow** — собственная реализация с фокусом на follow-up, прозрачности статусов, workspace isolation и интеграциях ITG.
- **Правило разработки:** сначала тесты и работоспособность существующего MVP, затем расширение функциональности без потери данных и прав доступа.

## 3. Что есть в текущем MVP (по коду и README, не по запуску)

- Backend: CRUD сделок, клиенты, стадии и воронки, запись и очистка follow-up, ограничения workspace, проверки связей и роли.
- Frontend: React Kanban, drag-and-drop, формы сделки, follow-up, поиск, фильтр «сегодня», обработка ошибок.
- PostgreSQL и Alembic; тесты backend и frontend присутствуют.
- Авторизация, сессии, рабочие пространства и роли присутствуют.
- **Не подтверждено в работающем окружении:** успешное выполнение тестов, полный E2E-сценарий, готовность к production.
- **Не реализовано по README:** история коммуникаций и задачи внутри карточки сделки; Dashboard, проекты, задачи, финансы, аналитика — демонстрационные экраны.

## 4. Roadmap

### P0 — техническая основа (перед расширением)

1. Запустить изолированные backend-тесты на PostgreSQL, frontend-тесты и сборку через `docker-compose.test.yml`.
2. Добавить Playwright E2E для цепочки: регистрация → workspace → клиент → сделка → смена стадии → follow-up → перезагрузка → сохранность данных.
3. Проверить отрицательные сценарии: чужой workspace, роль MANAGER, ошибки API, временные зоны, миграции, отсутствие утечек данных.
4. Включить проверки в CI и зафиксировать воспроизводимый зелёный результат.

**Критерий готовности:** все тесты проходят, E2E воспроизводим, миграции проходят на чистой БД; существующий CRUD не сломан.

### P1 — CRM для ежедневной работы

1. **Карточка сделки v2:** лента активностей, заметки, задачи, контакты, история смены стадий.
2. **Follow-up v2:** история завершённых действий (отдельная сущность), следующий контакт, ответственный, список «Кому написать сегодня», просроченные, напоминания.
3. **Контакты и клиенты:** полноценные карточки, привязка к сделкам, дубликаты и поиск.
4. **Настраиваемые воронки:** CRUD стадий, порядок, защита от удаления используемой стадии.

**Критерий готовности:** менеджер проходит рабочий день в CRM без внешнего списка напоминаний; действия сохраняются с автором и временем; роли соблюдены.

### P2 — операционная система студии

1. Задачи и календарь с назначениями и сроками.
2. Создание проекта из выигранной сделки; этапы проекта и исполнители.
3. Счета/документы и простые статусы оплаты.
4. Webhooks, интеграция n8n, входящие заявки с сайта ITG, логирование и повторная доставка событий.

### P3 — отчёты и расширение

1. Конверсия воронки, суммы по стадиям, просроченные follow-up, KPI менеджеров.
2. Конфигурируемые роли, расширенный поиск, экспорт и аудит действий.
3. Дальнейшие модули только после подтверждённой потребности и тестов.

## 5. Приоритетный пользовательский сценарий ITG

**Лид → клиент → сделка → следующий контакт → договор → проект → оплата → сопровождение.**

Для каждого перехода фиксировать событие, ответственного, дату и источник данных. Следующее действие — обязательный элемент процесса продаж, но не блокировать сохранение исторических сделок без follow-up.

## 7. Правила внесения изменений

1. Один модуль/сценарий — один небольшой PR с критериями приёмки.
2. Любая новая сущность: миграция, API, авторизация, тесты, UI и обработка ошибок.
3. Не изменять production, существующие данные и секреты без отдельного согласования.
4. Референсы не являются техническим заданием: сначала краткая спецификация UX и данных, затем код.
5. Не утверждать, что функция «работает», пока тесты или ручная проверка не подтверждены.

## 8. Первый следующий шаг

**P0: запустить существующий тестовый Docker-стек, исправить найденные ошибки и добавить E2E для сделки/follow-up.** Только после зелёных проверок начинать карточку сделки v2 и историю активностей.
